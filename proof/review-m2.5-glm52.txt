==== VERBATIM REVIEW ====
# M2 → M2.5 Review

## A. Entropy honesty (`src/rng.rs`)

### MUST-FIX
**A1. `h.update(d.to_le_bytes())` hashes the full 64-bit count but the entropy claim is only for the low 8 bits.** `src/rng.rs:gather` feeds `d.to_le_bytes()` (all 8 bytes) into the SHA-256 accumulator, yet `H_CLAIM = 0.1` is stated as "per 8-bit raw sample (low byte of each count)" and the MCV/lag-1 estimates in `init` operate only on `LOWB[i] = s = d as u8`. The in-kernel estimator never sees bytes 1–7 of the count, so the estimate says nothing about how much entropy lives in those bytes. The conditioning step, however, treats all 64 bits as entropic input. The arithmetic "0.1 bit × 10240 samples = 1024 credited bits vs 320 needed" is honest **only if** the upper 56 bits carry ≥ 0.1 bit/sample on average, which is not estimated at all. On a near-deterministic source (and the comment admits in-order Atoms are the weak case) the upper bytes are likely **less** entropic than the low byte, not more. Either (a) feed only `&[d as u8]` into the accumulator so the credit matches what is measured, or (b) measure and claim H over the 64-bit count. As written, the 320-bit seed threshold can be met with an unknown (possibly much lower) true entropy, which is the textbook 90B credit error. This is the single most important fix.

**A2. The TSC-race noise source can degenerate on a real in-order Atom.** The header comment asks exactly the right question and then does not answer it. On the N570 the TSC is core-clock-synchronous (Atom N570 TSC = invariant, rate = FSB/core). The `raw_delta` loop counts `touch()` iterations (a stride-4160 walk over a 2 MiB buffer) until the TSC advances `WINDOW` ticks. On an in-order core with interrupts off:
- The TSC increment per loop iteration is `TSC_per_iter = (cycles per touch) × 1` (deterministic-ish: a fixed L2-miss/DRAM loop).
- The count `n = WINDOW / TSC_per_iter + rounding`.
- The only jitter is DRAM refresh / memory-controller timing skew per touch, which the comment relies on but which may be ~constant on a single-channel NM10.

The QEMU evidence (lag-1 0.95–1.5 bits) is from **host scheduling noise** (TCG TSC steps in 1000-tick quanta, host OS preemption) — an effect that is absent on the N570 with interrupts off. The comment "QEMU numbers say nothing about the N570" is present but the code still uses the QEMU-derived `H_CLAIM = 0.1` as the production cutoff. The honest move is: **refuse to run SSH on the N570 until `rng=dump` has been measured on real hardware and the cutoff set from that**, not from a QEMU run that the comment itself disclaims. Currently `init` will happily pass startup on the N570 with a near-constant count (the RCT/APT may or may not catch it depending on how many distinct low bytes the DRAM skew produces) and then credit 0.1 bit/sample. This is a dishonest claim dressed with a caveat.

### SHOULD-FIX
**A3. RCT runs on the low byte; APT cutoff 507 is correct for the low-byte count under H=0.1, but the RCT cutoff should be 1 + ⌈30/0.1⌉ = 301 — verify.** `RCT_CUTOFF = 301` ✓ (`src/rng.rs`). APT: with W=512, H=0.1 ⇒ p=2^-0.1≈0.9339, want smallest C with P(Bin(511,p) ≥ C-1) ≤ 2^-30. Your claim is C=507. Sanity: mean ≈ 477.2, σ ≈ √(511·p·q) ≈ √(511·0.9339·0.0661) ≈ 5.63. 506-1 = 505 ⇒ (505-477.2)/5.63 ≈ 4.94 σ ⇒ tail ≈ 3.9e-7 ≈ 2^-21.3. That's > 2^-30. **507 is too low** to actually hold alpha = 2^-30 at H=0.1; you'd need C ≈ 510–511. The `tools/entropy-est.py --cutoffs 0.1` citation is the only authority; either the tool is wrong or the claim is wrong. Either way the in-code constant (507) does not match the stated alpha. Recompute precisely.

**A4. `mcv_milli` uses a 99% (z=2.576) upper bound but the standard 90B MCV estimator uses a 99% one-tailed bound with a correction; more importantly, `lag1_milli`'s "≥ 20 successors" gate means rows with < 20 transitions contribute 0 to `worst`, so a source that deterministically alternates between 2 values (each row has n≈2048, p=0.5, pu≈0.533, ⇒ 0.909 bit) passes with high lag-1 but is perfectly predictable given the previous sample.** The guard "catches serial correlation MCV cannot see" is right in spirit but the "≥ 20 successors" skip lets through the exact pathology it claims to catch. With a deterministic alternation A↔B, every row has n≈2048 so it's not skipped — actually this *is* caught. Retract concern; the gate is fine. (Leaving this as a NOTE that I checked it.)

**A5. RCT state is not reset across reseed boundaries but the APT window is.** `Health` persists across `gather` calls (good for RCT), but the APT only resets when `apt_i == APT_W`. Reseed batches are `BLOCK_N = 10240` samples; APT_W=512, so APT fires ~20 times per reseed — fine. No bug, just noting the coupling is subtle.

### NOTE
**A6. `rdrand32()` stuck check is "same value twice in a row" (one repeat).** M2's `fill` used "4 times in a row". The new check is stricter (good) but `rdrand32()` is only called once per `init` and once per `fill` when `USE_RDRAND`. The AMD all-ones erratum would need the *same* 64-bit value twice consecutively, which a stuck DRNG would produce. Fine. The 32-byte output is never zeroed after use, though — the `r` array lives on the stack. Minor key-hygiene gap.

**A7. `WINDOW` is set in `init` and read in `raw_delta` via `unsafe { WINDOW }` — fine, single-threaded.** But `tsc_granularity()` runs **before** `WINDOW` is set and is not health-tested; a dead TSC yields `g = 1`, `w = 32768`, and `raw_delta` returns 0 for every sample, which the RCT must catch (`rct_n` would hit 301 since all samples equal 0). The comment says the RCT "must" catch this. Good. But the `badjitter` cfg sets `tsc()` to a *constant* `0x4e43_3131`, not 0 — so `tsc_granularity` returns `g = u64::MAX` ⇒ `None` ⇒ `1`, and `raw_delta` counts touches until `0x4e43_3131 - 0x4e43_3131 < w` wraps… actually `tsc()` returns the same constant every call, so `start == t0` loop spins 2^16 times and returns 0. Same dead-timer path. Good.

## B. SATA / non-NIC hardware safety

### MUST-FIX
**B1. The 2 MiB UC map is applied to the page containing the NIC's MMIO BAR base, but `invlpg` of a 2 MiB page is wrong.** `nic.rs:mmio_window`:
```rust
let pde = addr_of_mut!(pd[(base >> 21) as usize]);
write_volatile(pde, read_volatile(pde) | (1 << 4) | (1 << 3)); // PCD | PWT
core::arch::asm!("invlpg [{}]", in(reg) base, options(nostack));
```
`pd` holds **2 MiB PDEs** (the boot.s comment says "4 x 512 2-MiB identity entries covering 0..4 GiB" — wait, `pd: .skip 4096 * 4` is 4 pages = 2048 entries × 2 MiB = 4 GiB, yes). Setting PCD|PWT on a 2 MiB PDE makes that whole 2 MiB UC. `invlpg` invalidates any page size the translation could produce, so this is correct for a 2 MiB PDE. **However**, the NIC's register window is 256 bytes; you're making a 2 MiB region UC, which is fine and conservative. No bug. Retracting — this is sound. The alignment check (`base & 0xFF`) is weaker than the 2 MiB alignment the PDE requires (`base & 0x1F_FFFF`), but the BAR base will be 2 MiB-aligned only if the BAR is ≥ 2 MiB. RTL8101E's BAR is typically 256 bytes, so `base` will be 256-byte-aligned but **not** 2 MiB-aligned. **This is a real bug**: `pd[(base >> 21)]` maps the 2 MiB region *containing* the BAR, which is correct for making that span UC, but if the BAR is at e.g. `0xfebf_e000`, the PDE for `0xfebe_0000..0xfec0_0000` is modified — covering 2 MiB that includes unrelated MMIO (potentially the SATA BAR if it lives in the same 2 MiB, which on NM10 it likely does: NM10 IOAPIC/RCBA at 0xfed0_0000, AHCI at 0xfeb? region). Making a 2 MiB span UC that overlaps the SATA controller's MMIO window is **not** a config-space or port touch, so it doesn't violate spec rule 4's letter, but it changes caching for the SATA BAR region, which could disturb an iPXE-left-running AHCI. More importantly: you intend to avoid the SATA BAR; `clear_of_storage(base, ...)` checks the NIC's 256-byte window, but the UC PDE covers a 2 MiB span that the SATA BAR could sit inside. The validation guards the 256 B window, the mapping affects 2 MiB. **MUST-FIX**: either (a) validate the whole 2 MiB span against storage BARs, or (b) use a 4 KiB PTE (split the PDE into a PT) so only the actual page goes UC. This is the second most important fix.

### SHOULD-FIX
**B2. `set_pci_cmd` writes the full 32-bit command/status word with status=0, which clears RW1C status bits the BIOS/iPXE may have set.** `nic.rs:set_pci_cmd`: `pci::write32(b, 0x04, (cmd & !clear) | set)` where `cmd = pci::read32(b, 0x04) & 0xFFFF` — so the high 16 bits (status) are written as 0. Status bits are RW1C, so writing 0 clears none — **actually writing 0 to a RW1C bit does NOT clear it** (write 1 to clear). Writing 0 is a no-op on status. Fine. Retract.

**B3. `clear_of_storage` uses `1u64 << s.trailing_zeros().min(32)` as the span.** If a storage BAR base is 0 (unassigned), `trailing_zeros()` = 64, `min(32)` = 32, span = 4 GiB. A zero base storage BAR would block the entire < 4 GiB region. Defensive but fine (no real storage BAR is at 0). If `base == 0` for the NIC you already refuse. OK.

**B4. Bridge walk: `walk_bus` reads the secondary bus number (`read32(b, 0x18) >> 8`) but a type-1 header's secondary/subordinate are at offsets 0x18 (sec) and 0x19 (sub). You don't check subordinate, so a bridge whose subordinate < its sec but whose sec is a valid bus will still recurse, and the `seen[]` guard + budget=32 prevents infinite loops.** A bridge with sec=0 is skipped (`sec != 0`), good. The budget of 32 buses is small but the NC110 has at most ~2 buses. The depth limit 8 is fine. No infinite loop. NOTE only.

## C. RTL8101E correctness vs r8169 v6.12

### MUST-FIX
**C1. `xid_version` mask `0xFCF` vs r8169's `0x7cf`/`0x7c8` family, and the `VER_10` entry `(0x7c8, 0x340, 10)`.** r8169 `rtl8169_get_mac_version` (v6.12 ~line 5420) does `RTL_GIGA_MAC_VER_v…` matched by `TxConfig >> 20` with masks `0x7cf00000` / `0x7c800000`? Actually r8169 does `(TPPOLL_XIDN | mac_version)` table where the XID is `(TxConfig & 0x7cf00000) >> 20` then matched against `(mask, val)` pairs. You compute `xid = (txc >> 20) & 0xFCF`. r8169 uses `xid = (txc >> 20) & 0x3ff` then matches `(xid & mask) == val` with masks like `0x7cf`. **`0xFCF` is not a mask r8169 uses** — I think you've taken a shortcut collapsing `0x7cf` and `0x7c8` (the high-nibble 0x7 is fixed by the `>> 20` of a value < 0x1_0000_0000? no — `TxConfig` is 32-bit, `>> 20` leaves 12 bits, and the high bits of the XID encode the family). If r8169 masks with `0x7cf`, that's 0x7cf = 0b0111_1100_1111; your `0xFCF` = 0b1111_1100_1111 — you keep the top nibble (0x8–0xF) which r8169 deliberately discards. This means your match can accept XIDs r8169 rejects (e.g. 0x840 would match your `0x7c8`? no — `0x840 & 0xFCF = 0x840 & 0xFCF` = `0x840`... `0x840 & 0x0FCF = 0x040`, so `(0xFCF, v)` with v in {0x340, 0x248, 0x348, ...} — `0x040` ≠ any). Hmm, this is getting tangled; the real question is whether your collapsed table can mis-identify an 8105E/8402 (which share 10ec:8136) as a VER_07..10 and proceed to drive it with the wrong init. Given you only support 8101E/8102E/8103E and the 810x family is what 10ec:8136 covers, the practical risk is low, but the `0xFCF` mask is **not** what r8169 uses and the comment cites r8169 lines as authority. This is a correctness-of-citation issue; on a non-8101E 8136 (e.g. an 8105E in a different NC110 variant) you could mis-drive. **MUST-FIX the mask to match r8169 exactly** or document that the XID gate is intentionally loose. I'd tighten it.

**C2. `init_8101e` skips the per-version `hw_config` and PHY config tables and admits it ("NOT done (documented gap)").** For VER_07/08/09 (8102E) r8169 calls `rtl8102e_hw_phy_config` / `rtl_hw_start_8102e_{1,2,3}` which write PHY registers (MII registers via PHYAR) and EPHY. Without these, the PHY may not link (the `phystatus` LINK_STATUS poll at the end will time out at 5 s and you'll proceed anyway — `Ok(())` is returned regardless of link). The most likely failure mode on real hardware: **no link / no carrier**, and even if link comes up the analog tuning (AFE, TX amplitude, etc.) is unset, so you may see high CRC errors or no RX. The comment is honest; the risk is real. **SHOULD-FIX**: at minimum, return `Err` if link doesn't come up in 5 s rather than `Ok(())` with a "DOWN" log — otherwise SSH proceeds with a dead link.

**C3. `init_8101e` returns `Ok(())` even when PHY link is DOWN.** The 5 s poll loop ends and you print "DOWN after 5 s" but still return `Ok(())`. `kmain` then calls `ssh::run`. SSH will hang on TCP connect. This is a SHOULD-FIX (return `Err`) but coupled with C2 it's the dominant failure mode on the N570.

### SHOULD-FIX
**C4. `rx_err` bit for 8101E is `1 << 21` (r8169 `RxRES`), for 8139C+ is `1 << 20` (`RxError`).** Correct per your tables; good. The `rx_len_mask` 0x3FFF for 8101E vs 0x1FFF for 8139C+ — r8169 uses `(status & 0x1fff)` for 8168 but 8101E (8136) uses `(status & RsvdMask)`? Linux r8169 `rtl8169_rx_one` does `pkt_size = rtl8169_desc_opts1.frp & RsvdMask` where `RsvdMask = 0x7FF`?? Actually `RsvdMask` in r8169 is `0x1fff` for the length field across all r8169. Let me not overclaim — your CITES table pins it to `r8169_main.c:4630 "pkt_size"`. Trust the host test (40 values checked). NOTE.

**C5. `mdio_write`/`mdio_read` use `reg & 0x1F` — 5-bit PHY register.** r8169's PHYAR uses bits 0–15 for data and 16–20 for regad (5 bits, MII 5-bit reg). Correct. The `PHYAR_FLAG` is bit 31. The write path sets flag, waits for it to **clear**; the read path clears flag, waits for it to **set**. This matches r8169. Good.

**C6. The 8101E path does `set_pci_cmd(b, 0, PCI_CMD_BM | PCI_CMD_IO)` *before* `mmio_window` (bus master OFF to stop iPXE DMA), then `set_pci_cmd(b, PCI_CMD_MEM, PCI_CMD_BM | PCI_CMD_IO)` *after* `mmio_window` (turn on MEM + still no BM), then later `set_pci_cmd(self.bdf, PCI_CMD_BM, 0)` *after* rings are programmed.** This is the right order and a real defense against iPXE-left-DMA. Good. But note: `set_pci_cmd` reads the current cmd and only sets/clears the named bits; between the first `set_pci_cmd(0, BM|IO)` and the second `set_pci_cmd(MEM, BM|IO)`, if the BIOS had already set MEM (likely), the first call doesn't clear MEM, so MEM is already on during `mmio_window`'s PDE write — fine, you're just reading config/MMIO. OK.

## Entropy claim summary

The header comment is *almost* honest. The two dishonest bits:

1. "Credit 0.1 bit/sample, 10240 samples per key = 1024 credited bits vs 320 needed" — the credit is applied to 64-bit counts, the estimate to 8-bit. **A1.**
2. The QEMU caveat is present but the production cutoff is derived from the disclaimed QEMU data. **A2.**

The RCT cutoff (301) is right. The APT cutoff (507) I suspect is too low for alpha=2^-30 at H=0.1 — **A3**.

## Score: 6/10

Most of the structure is sound — the NIC probe/MMMO/storage-guard ordering is careful, the bridge walk is bounded, the key module is clean, the ratchet is a reasonable extractor-style construction, and the honesty commentary is *more* present than absent. But the entropy credit/measure mismatch (A1) is a real safety hole, the 2 MiB UC mapping can affect storage MMIO (B1), the 8101E init will likely not link on the actual target hardware and proceeds even when it doesn't (C2/C3), and the APT cutoff doesn't meet the stated alpha (A3).

**Single most important fix**: make the entropy credit match what is estimated — feed only the low byte (or measure and claim H over the 64-bit count) so the 320-bit seed threshold is honest.
