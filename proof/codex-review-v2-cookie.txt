//! ACPI tables, read-only: find the RSDP in the BIOS area, walk the RSDT, and hand table bytes to bmctl (`acpi <sig>
//! <off>`, e.g. FACP, DSDT, FACS), so an agent can read the firmware's description of the battery, the EC and the
//! sleep states without booting Linux. Nothing is written.
use core::ptr::read_volatile;

fn rd32(a: u64) -> u32 {
    unsafe { read_volatile(a as *const u32) }
}

fn sum_ok(a: u64, len: usize) -> bool {
    (0..len).fold(0u8, |s, i| s.wrapping_add(unsafe { read_volatile((a + i as u64) as *const u8) })) == 0
}

fn rsdt() -> Option<u64> {
    for a in (0xE0000u64..0x100000).step_by(16) {
        if unsafe { read_volatile(a as *const [u8; 8]) } == *b"RSD PTR " && sum_ok(a, 20) {
            return Some(rd32(a + 16) as u64);
        }
    }
    None
}

/// (address, length) of the table with signature `sig`; "DSDT" and "FACS" are found through the FADT.
pub fn table(sig: &[u8; 4]) -> Option<(u64, u32)> {
    let r = rsdt()?;
    if unsafe { read_volatile(r as *const [u8; 4]) } != *b"RSDT" {
        return None;
    }
    let n = (rd32(r + 4) as u64).saturating_sub(36) / 4;
    let mut fadt = None;
    for i in 0..n.min(64) {
        let t = rd32(r + 36 + 4 * i) as u64;
        let s = unsafe { read_volatile(t as *const [u8; 4]) };
        if s == *sig {
            return Some((t, rd32(t + 4)));
        }
        if s == *b"FACP" {
            fadt = Some(t);
        }
    }
    let f = fadt?;
    let t = match sig {
        b"DSDT" => rd32(f + 40) as u64,
        b"FACS" => rd32(f + 36) as u64,
        _ => return None,
    };
    let len = if sig == b"FACS" { rd32(t + 4) } else { rd32(t + 4) };
    (unsafe { read_volatile(t as *const [u8; 4]) } == *sig).then_some((t, len))
}

/// Up to `out.len()` bytes of table `sig` from offset `off`; the table length, or None if absent.
pub fn read(sig: &[u8; 4], off: usize, out: &mut [u8]) -> Option<(u32, usize)> {
    let (a, len) = table(sig)?;
    let len = len.min(1 << 20);
    let n = out.len().min((len as usize).saturating_sub(off));
    for (i, b) in out[..n].iter_mut().enumerate() {

def rpc(raw, want=lambda d: True):
    """Send `raw`, return the first reply from the target that `want` accepts. Stale datagrams (late answers to
    an earlier timed-out attempt) are drained before sending and skipped while waiting, so a resend can never
    leave the client one reply behind."""
    host = socket.gethostbyname(a.host)
    for _ in range(3):  # a retry of the same frame gets the kernel's cached reply, nothing runs twice
        s.setblocking(False)
        try:
            while True:
                s.recvfrom(2048)
        except (BlockingIOError, OSError):
            pass
        s.settimeout(TIMEOUT[0])
        s.sendto(raw, (a.host, a.port))
        end = time.monotonic() + TIMEOUT[0]
        try:
            while time.monotonic() < end:
                d, src = s.recvfrom(2048)
                if src[0] == host and want(d):
                    return d
        except socket.timeout:
            continue
    sys.exit(f"no reply from {a.host}:{a.port}")

//! Monotonic milliseconds from the TSC, calibrated once against PIT channel 2 (gate via port 0x61).
use crate::port::{inb, outb, rdtsc};

static mut TSC_PER_MS: u64 = 1_000_000; // fallback guess (1 GHz) if calibration fails
static mut T0: u64 = 0;

pub fn init() -> u64 {
    unsafe {
        // PIT ch2, mode 0, lobyte/hibyte, count for 10 ms at 1.193182 MHz.
        const COUNT: u16 = 11932;
        let g = inb(0x61);
        outb(0x61, (g & 0xFD) | 0x01); // gate on, speaker off
        outb(0x43, 0b1011_0000);
        outb(0x42, COUNT as u8);
        outb(0x42, (COUNT >> 8) as u8);
        // Re-trigger: toggle gate low->high so mode 0 starts counting now.
        let g = inb(0x61);
        outb(0x61, g & 0xFE);
        outb(0x61, g | 0x01);
        let a = rdtsc();
        let mut spins: u64 = 0;
        while inb(0x61) & 0x20 == 0 && spins < 200_000_000 {
            spins += 1;
        }
        let b = rdtsc();
        if spins < 200_000_000 && b > a {
            TSC_PER_MS = ((b - a) / 10).max(1);
        }
        T0 = rdtsc();
        TSC_PER_MS
    }
}

Most of the cryptographic structure is sound, but the promoted ring breaks replay protection and can cause response-key/nonce reuse. **6/10 as submitted.** This is a source review; I did not run QEMU.

**MUST-FIX**

1. **The 64-entry ring allows authenticated commands to execute again.** In [bmctl.rs](~/nc110-baremetal/src/bmctl.rs:470):

   ```rust
   && !self.promoted[..self.promoted_n.min(64)].contains(&sid);
   ```
   ```rust
   self.promoted[self.promoted_n % 64] = sid;
   self.promoted_n += 1;
   ```

   Concrete sequence:

   - Capture an accepted first frame, such as `ping` at sequence 1.
   - Allow 64 other sessions to promote within its cookie’s validity window. Those promotions also evict the original inactive session from the 16-entry live table.
   - Replay the original frame from its original endpoint, or spoof that endpoint.

   Its cookie still recomputes, its SID has disappeared from the ring, and the candidate starts with `last_seq: 0`. Authentication succeeds and the command runs again. An observer needs legitimate authenticated traffic to supply those promotions; a `who2` flood alone cannot do it.

   This also **reuses the response AEAD key and nonce**: the repeated `ping` produces a different uptime under the same `K2C || 1`. That is more serious than duplicate command execution.

   Keep replay records until their cookies can no longer be accepted, and fail closed if storage fills. Merely increasing 64 postpones the failure. For a robust redesign, bind the full issuance bucket into the traffic key and authenticated header, so a later 32-bit cookie collision cannot recreate an old key.

2. **Unauthenticated malformed replies can crash the client before verification.** [bmctl.py](~/nc110-baremetal/tools/bmctl.py:89):

   ```python
   bid, sess, b = bytes.fromhex(w[3]), int(w[5]), int(w[7])
   ... struct.pack("<IB", sess, b) ...
   ...
   except ValueError:
   ```

   A reply containing `session 4294967296` or `bucket 256` raises `struct.error`, which is not a `ValueError`. I confirmed that exception behavior locally. No valid check is needed; the packet only needs to pass the source-IP filter. The v1 branch and flood harness have the same issue.

   Validate integer ranges and boot-ID length, and catch `struct.error`. Match the source port too, although that does not prevent spoofing.

3. **Case 13 depends on an untracked file.** [bmctl-q35-test.sh](~/nc110-baremetal/tools/bmctl-q35-test.sh:67) executes:

   ```python
   "tools/bmctl_v1_head.py"
   ```

   That file exists locally but is not tracked. A clean checkout of this patch fails case 13. Include the fixture or make the test self-contained.

**SHOULD**

- **Validate FACS before performing unconditional boot-time accesses.** [acpi.rs](~/nc110-baremetal/src/acpi.rs:66) explicitly discards the length:

  ```rust
  let (f, _) = table(b"FACS")?;
  ```

  It then reads through offset 31 and potentially writes both vectors. Reject invalid addresses, insufficient lengths, and invalid alignment before typed volatile accesses; validate the FADT pointer path as well. Moving this into every boot makes malformed firmware tables a startup failure rather than an explicitly requested ACPI-operation failure.

  **Alignment itself is not a demonstrated bug on compliant firmware:** FACS is 64-byte aligned, making offsets 12 and 24 suitable for these accesses. [ACPI specification](https://uefi.org/specs/ACPI/6.6/05_ACPI_Software_Programming_Model.html)

  **Version <1 alone is also not a convincing reason to prohibit zeroing X.** Linux ACPICA clears X even for version 0, guarded by `facs->length > 32`. The missing length guard is the stronger finding here. [ACPICA implementation](https://raw.githubusercontent.com/torvalds/linux/master/drivers/acpi/acpica/hwxfsleep.c)

- **The flood fix improves admission but does not guarantee service.** Every `who2` performs two SHA-256 computations, formatting, and a send attempt, without a rate limit—even when TX is full. Also:

  ```rust
  RX_META: ... 64
  TX_META: ... 8
  ```

  A batch can fill all eight TX slots with unauthenticated replies before processing a legitimate command. Its response is cached, but sending fails; retries help only if they encounter free slots. Reserve response capacity for authenticated traffic or skip handshake work when its reply budget is exhausted. Avoid restoring the globally shared admission bottleneck that motivated this change.

  The receive budget and 64-packet drain bound work per pass. They do not prevent a flood from filling the queue or dropping legitimate packets.

- **Make collision failures recoverable.** Lookup uses:

  ```rust
  x.id == sid && x.peer == Some(from)
  ```

  A new cookie colliding with a live SID on the same endpoint selects the old key, so the new client fails authentication. On another endpoint, the global promoted-SID check rejects it while that SID remains recorded. These are availability failures, not automatic cross-session authentication. A fresh-nonce handshake retry would recover; the current client retries the same command frame and eventually exits.

**Security questions that mostly check out**

| Question | Assessment |
|---|---|
| Two ordinary sessions have the same 32-bit cookie | Different `Nc` values produce different traffic keys. SID collision alone does not reuse a key. |
| Can keys repeat? | Yes if boot, SID, and `Nc` repeat. The ring replay above causes this directly. Endpoint and bucket are absent from the KDF. |
| Can an unrelated session accept a captured frame? | Not merely because its SID collides: the different key rejects the tag. Live-session lookup ignores the supplied `Nc` and bucket, but authentication still uses the stored key and existing sequence state. |
| Blind cookie forgery | Approximately \(2^{32}\) guesses for a selected endpoint/nonce/bucket. Passing that gate still requires a valid AEAD tag; this is not a 32-bit command-authentication scheme. |
| Birthday collisions | About 77,000 independent cookies gives a 50% chance of some pair colliding. That is not the cost of hitting a particular live session, nor does an arbitrary pair imply key reuse. |
| Low-byte bucket wrap | Correctly disambiguated by recomputing with full current/previous `u32` buckets. After 256 buckets, the low byte repeats but the hash input differs; there is no deterministic 128-minute replay. |

**MUST-FIX**

1. **The 64-entry ring allows authenticated commands to execute again.** In [bmctl.rs](~/nc110-baremetal/src/bmctl.rs:470):

   ```rust
   && !self.promoted[..self.promoted_n.min(64)].contains(&sid);
   ```
   ```rust
   self.promoted[self.promoted_n % 64] = sid;
   self.promoted_n += 1;
   ```

   Concrete sequence:

   - Capture an accepted first frame, such as `ping` at sequence 1.
   - Allow 64 other sessions to promote within its cookie’s validity window. Those promotions also evict the original inactive session from the 16-entry live table.
   - Replay the original frame from its original endpoint, or spoof that endpoint.

   Its cookie still recomputes, its SID has disappeared from the ring, and the candidate starts with `last_seq: 0`. Authentication succeeds and the command runs again. An observer needs legitimate authenticated traffic to supply those promotions; a `who2` flood alone cannot do it.

   This also **reuses the response AEAD key and nonce**: the repeated `ping` produces a different uptime under the same `K2C || 1`. That is more serious than duplicate command execution.

   Keep replay records until their cookies can no longer be accepted, and fail closed if storage fills. Merely increasing 64 postpones the failure. For a robust redesign, bind the full issuance bucket into the traffic key and authenticated header, so a later 32-bit cookie collision cannot recreate an old key.

2. **Unauthenticated malformed replies can crash the client before verification.** [bmctl.py](~/nc110-baremetal/tools/bmctl.py:89):

   ```python
   bid, sess, b = bytes.fromhex(w[3]), int(w[5]), int(w[7])
   ... struct.pack("<IB", sess, b) ...
   ...
   except ValueError:
   ```

   A reply containing `session 4294967296` or `bucket 256` raises `struct.error`, which is not a `ValueError`. I confirmed that exception behavior locally. No valid check is needed; the packet only needs to pass the source-IP filter. The v1 branch and flood harness have the same issue.

   Validate integer ranges and boot-ID length, and catch `struct.error`. Match the source port too, although that does not prevent spoofing.

3. **Case 13 depends on an untracked file.** [bmctl-q35-test.sh](~/nc110-baremetal/tools/bmctl-q35-test.sh:67) executes:

   ```python

   ```

   That file exists locally but is not tracked. A clean checkout of this patch fails case 13. Include the fixture or make the test self-contained.

**SHOULD**

- **Validate FACS before performing unconditional boot-time accesses.** [acpi.rs](~/nc110-baremetal/src/acpi.rs:66) explicitly discards the length:

  ```rust
  let (f, _) = table(b"FACS")?;
  ```

  It then reads through offset 31 and potentially writes both vectors. Reject invalid addresses, insufficient lengths, and invalid alignment before typed volatile accesses; validate the FADT pointer path as well. Moving this into every boot makes malformed firmware tables a startup failure rather than an explicitly requested ACPI-operation failure.

  **Alignment itself is not a demonstrated bug on compliant firmware:** FACS is 64-byte aligned, making offsets 12 and 24 suitable for these accesses. [ACPI specification](https://uefi.org/specs/ACPI/6.6/05_ACPI_Software_Programming_Model.html)

  **Version <1 alone is also not a convincing reason to prohibit zeroing X.** Linux ACPICA clears X even for version 0, guarded by `facs->length > 32`. The missing length guard is the stronger finding here. [ACPICA implementation](https://raw.githubusercontent.com/torvalds/linux/master/drivers/acpi/acpica/hwxfsleep.c)

- **The flood fix improves admission but does not guarantee service.** Every `who2` performs two SHA-256 computations, formatting, and a send attempt, without a rate limit—even when TX is full. Also:

  ```rust
  RX_META: ... 64
  TX_META: ... 8
  ```

  A batch can fill all eight TX slots with unauthenticated replies before processing a legitimate command. Its response is cached, but sending fails; retries help only if they encounter free slots. Reserve response capacity for authenticated traffic or skip handshake work when its reply budget is exhausted. Avoid restoring the globally shared admission bottleneck that motivated this change.

  The receive budget and 64-packet drain bound work per pass. They do not prevent a flood from filling the queue or dropping legitimate packets.

- **Make collision failures recoverable.** Lookup uses:

  ```rust
  x.id == sid && x.peer == Some(from)
  ```

  A new cookie colliding with a live SID on the same endpoint selects the old key, so the new client fails authentication. On another endpoint, the global promoted-SID check rejects it while that SID remains recorded. These are availability failures, not automatic cross-session authentication. A fresh-nonce handshake retry would recover; the current client retries the same command frame and eventually exits.
